# Прогресс проекта: Сегментация клиентов + предсказание оттока

## О проекте

Цель проекта — построить полный ML-пайплайн для интернет-магазина, 
решающий две связанные бизнес-задачи:

1. **Сегментация клиентов** — разбить всех клиентов на группы по 
   поведению (как давно покупал, как часто, на какую сумму), без 
   какой-либо разметки. Это unsupervised задача — модель сама находит 
   закономерности в данных. Используется RFM-анализ + кластеризация 
   KMeans.

2. **Предсказание оттока** — для каждого клиента предсказать вероятность 
   того что он перестанет покупать в ближайшее время. Это supervised 
   задача — модель учится на исторических примерах "кто ушёл / кто 
   остался". Кластер из задачи 1 используется как одна из фичей — то 
   есть две задачи органично связаны, не существуют отдельно друг от 
   друга.

В конце — Streamlit-демо: загружаешь CSV с клиентами, получаешь 
распределение по кластерам, вероятность оттока для каждого клиента и 
объяснение (через SHAP) каких факторов на это влияет больше всего.

Это пет-проект для портфолио ML-инженера, цель — показать полный цикл 
работы: от грязных сырых данных, через обоснованные решения по 
очистке и feature engineering, до интерпретируемой модели с понятными 
бизнес-выводами.

## Полный план этапов

**Этап 0 — Подготовка (готово)**
Структура репозитория (data/raw, data/processed, notebooks, src, app, 
models), git-репозиторий на GitHub, выбор датасета Online Retail II.

**Этап 1 — EDA (готово)**
Ноутбук `01_eda.ipynb`. Загрузка датасета, изучение колонок, поиск 
пропусков и аномалий (отрицательный Quantity = возвраты, Price = 0, 
пропуски в Customer ID). Принятые решения по каждой проблеме 
задокументированы прямо в ноутбуке.

**Этап 2 — Очистка + RFM (готово)**
Ноутбук `02_rfm.ipynb`. Применение решений по очистке из этапа 1. 
Расчёт трёх метрик на каждого клиента: Recency (дней с последней 
покупки), Frequency (число уникальных заказов), Monetary (сумма 
покупок с учётом возвратов). Результат сохранён в 
`data/processed/rfm.csv`.

**Этап 3 — Кластеризация (готово)**
Ноутбук `03_clustering.ipynb`. Нормализация RFM через StandardScaler. 
Подбор оптимального числа кластеров (метод локтя + silhouette score). 
Обнаружение и устранение проблемы с выбросами (метод IQR). Финальная 
модель KMeans с K=4, интерпретация каждого кластера через средние 
значения RFM. Результат сохранён в `data/processed/rfm_with_clusters.csv`.

**Этап 4 — Feature Engineering для churn (готово)**
Ноутбук `04_features.ipynb`. Сконструирована целевая переменная через 
временной сплит (утечка выявлена и устранена), собран финальный набор 
фичей. Подробности ниже в разделе "Этап 4".

**Этап 5 — Бейзлайн-модель (готово)**
LogisticRegression на признаках из этапа 4. Подробности ниже в разделе
"Этап 5". Оригинальный план:
Обучить простую LogisticRegression на фичах из этапа 4. Посчитать 
метрики (ROC-AUC, Precision, Recall, F1 — не accuracy, так как классы 
скорее всего несбалансированы). Это точка отсчёта для сравнения с 
более сложными моделями.

**Этап 6 — Основная модель (готово)**
CatBoost проверен (из коробки → early stopping → grid), не побил бейзлайн —
все модели ~0.69 ROC-AUC (data-bound). Финальная модель — LogisticRegression
по бритве Оккама. Подробности ниже в разделе "Этап 6".

**Этап 7 — Интерпретация (не начато)**
SHAP-анализ — какие фичи сильнее всего влияют на предсказание оттока, 
в среднем и для конкретных клиентов. Анализ ошибок модели — есть ли 
сегменты (например конкретный кластер) где модель ошибается чаще, и 
почему. Проверить гипотезу — помогает ли фича "кластер" предсказанию 
(метрика с этой фичей против метрики без неё).

**Этап 8 — Streamlit-демо (не начато)**
Веб-интерфейс: загрузка CSV с клиентами, вывод распределения по 
кластерам (графики), таблица с вероятностью оттока по каждому клиенту, 
топ-факторы риска (SHAP) для выбранного клиента.

**Этап 9 — README и оформление (не начато)**
Финальное README с постановкой задачи, описанием пайплайна, таблицей 
метрик, описанием кластеров, ключевыми выводами, скриншотами 
Streamlit, инструкцией запуска.

## Этап 2 — RFM (готово)
Ноутбук: `notebooks/02_rfm.ipynb`

- Очистка: удалены строки с пустым Customer ID и Price = 0
- Итого для анализа: 417 503 строки
- Посчитаны метрики на клиента: Recency (дни с последней покупки), 
  Frequency (число уникальных Invoice), Monetary (Quantity * Price, 
  с учётом возвратов)
- Удалены клиенты с Monetary <= 0 (возвраты без истории покупок в 
  выборке — артефакт данных, не реальное поведение)
- Итог: 4283 клиента
- Результат сохранён: `data/processed/rfm.csv`

## Этап 3 — Кластеризация (готово)
Ноутбук: `notebooks/03_clustering.ipynb`

- Нормализация через StandardScaler (Recency, Frequency, Monetary)
- Первый прогон KMeans на исходных данных дал сильный дисбаланс 
  кластеров (5 / 54 / 1016 / 3208) — из-за выбросов с экстремальными 
  Frequency/Monetary
- Диагностика через `describe()`: разница между 75-м перцентилем и 
  максимумом — 45x по Frequency, ~200x по Monetary
- Удаление выбросов методом IQR (правило Тьюки, коэффициент 1.5) 
  по Frequency и Monetary. Recency не трогали — большие значения там 
  естественны (давно неактивный клиент), не аномалия
- После очистки: 3781 клиент (удалено ~500 выбросов)
- Повторный выбор K на чистых данных: метод локтя + silhouette score
- **Важно:** KMeans без `random_state` даёт невоспроизводимые 
  результаты между запусками. Зафиксировано `random_state=44, 
  n_init=10` во всех вызовах
- Финальное K=4 (компромисс — silhouette давал максимум на K=2-3, 
  но недостаточно детализации для бизнеса)
- 4 кластера с интерпретацией:
  - **Лояльные** — Recency низкий, Frequency высокий, Monetary высокий
  - **Обычные** — средние значения по всем метрикам
  - **Новые** — Recency низкий, но Frequency и Monetary низкие 
    (осторожная интерпретация — это предположение, не подтверждённый 
    факт, нет даты первой покупки в данных)
  - **Группа риска** — Recency очень высокий, Frequency и Monetary низкие
- Имена кластеров привязаны к номерам через словарь `cluster_names` — 
  **хрупкое место**: если изменится random_state или данные, числа 
  могут не совпасть с номерами кластеров. Нужно протестировать после 
  любых изменений выше по ноутбуку (проверить таблицу 
  `groupby('Cluster').mean()` перед тем как доверять словарю)
- Результат сохранён: `data/processed/rfm_with_clusters.csv`
- Сохранены артефакты препроцессинга: `models/scaler.pkl`, 
  `models/kmeans_model.pkl`, `models/outlier_bounds.pkl` (границы IQR)

## Этап 4 — Feature Engineering для churn (готово)
Ноутбук: `notebooks/04_features.ipynb`

- Обоснование порога оттока: интервалы между заказами, 90-й перцентиль
  = 86 дней, 95-й = 130. Выбран 86 (цена пропуска ушедшего клиента выше
  цены ложной тревоги)
- **Найдена и устранена утечка целевой переменной.** Наивный вариант
  `churn = Recency > 86` делает метку функцией признака — модель просто
  списывает ответ. Наивный блок намеренно оставлен в ноутбуке с разбором
- **Временной сплит:** T = max(InvoiceDate) − 90 дней = 2010-09-10.
  Признаки считаются по данным до T, целевая переменная — по факту
  покупки после T. Метка и признаки берутся из разных периодов
- Функция `compute_rfm(data, reference_date)` вынесена в 
  `src/features.py` и переиспользуется (опорная дата — параметр)
- Клиенты, впервые купившие после T, исключены — на момент T у них нет
  истории, признаки считать не из чего
- Выбросы отфильтрованы границами этапа 3 из `models/outlier_bounds.pkl`
  (не пересчитываются — часть зафиксированного препроцессинга, по той же
  логике, что `scaler.transform`, а не `fit_transform`)
- Кластер добавлен применением сохранённых `scaler.transform` +
  `kmeans.predict` к before-данным (не переобучая)
- Итог: **3072 клиента**, целевая переменная 1716 / 1356 (44.1% оттока)
- Проверка отсутствия утечки: диапазоны Recency у обоих классов
  полностью перекрываются (0–283), различаются только средние
  (~80 против ~117) — признак информативен, но не детерминирует ответ
- Результат сохранён: `data/processed/churn_dataset.csv`

## Этап 5 — Бейзлайн-модель (готово)
Ноутбук: `notebooks/05_baseline_model.ipynb`

- `Customer ID` вынесен в индекс (не признак, но связь с клиентом сохранена)
- Признаки: Recency, Frequency, Monetary + Cluster через one-hot
  (`get_dummies`, `drop_first=True` — против мультиколлинеарности у линейной
  модели). `Cluster_name` выброшен как текстовый дубль `Cluster`
- Train/test split 80/20, `stratify=y`. Случайный split здесь корректен:
  временная структура уже учтена на этапе 4 (все строки — снимок на один T),
  поэтому TimeSeriesSplit не нужен
- StandardScaler: `fit` только на train, `transform` на test (без утечки),
  масштабируются только 3 числовые колонки, dummy и `y` не трогаются
- Модель: LogisticRegression (max_iter=1000)
- **Метрики на test (порог 0.5):** ROC-AUC 0.691, Precision 0.590, Recall 0.590, F1 0.590
- ROC-AUC в здоровом диапазоне (не ~1.0) — подтверждает, что утечки нет
- **Подбор порога под Recall:** по precision-recall curve (выбор на train, без
  утечки) порог снижен 0.5 → ~0.42 под цель Recall ≥ 0.75. Результат на test:
  Recall 0.590 → 0.738, Precision 0.590 → 0.557, F1 0.590 → 0.635 (F1 вырос —
  0.5 не был оптимален). Обоснование: пропуск ушедшего дороже ложной тревоги
- **Модель сохранена:** `models/churn_model.pkl`, `churn_scaler.pkl`,
  `churn_meta.pkl` (порог + список признаков) — для этапов 7–8 (загрузка, не
  переобучение)

## Этап 6 — Основная модель (готово)
Ноутбук: `notebooks/06_main_model.ipynb`

- CatBoost на тех же признаках (Cluster как категория через `cat_features`,
  без one-hot и масштабирования — деревьям не нужно)
- Проверен в три захода: из коробки (1000 деревьев) → диагностика
  переобучения (train ROC-AUC 0.84 vs test 0.69) → early stopping (val-выборка,
  НЕ test) → grid search (нативный `model.grid_search`, т.к. sklearn
  GridSearchCV не клонирует CatBoost)
- **Итог сравнения (ROC-AUC на test):** все модели — логрег и все версии
  CatBoost — в коридоре ~0.686–0.696, разброс в пределах шума (точные числа —
  в таблице ноутбука; CatBoost слегка недетерминирован между прогонами)
- **Вывод: data-bound.** Все модели упёрлись в один потолок — его задают
  4 признака, а не сложность модели. Финальная модель — LogisticRegression по
  бритве Оккама (равное качество → берём простую и интерпретируемую)
- Функция `evaluate()` вынесена в `src/evaluation.py` (переиспользуется)

## Эксперимент — расширение признаков (готово, результат отрицательный)

**Гипотеза:** 4 RFM-признака дают потолок ~0.69; поведенческие признаки его поднимут.

**Что сделано:** в `src/features.py` добавлена функция `compute_features` — к RFM
досчитывает 5 признаков (все по окну `before`, без утечки):
- `Tenure` — дни с первой покупки клиента;
- `PurchaseRate` — Frequency / Tenure (интенсивность);
- `IntervalMean` — средний интервал между заказами;
- `SinglePurchase` — флаг «купил только раз» (для одноразовиков `IntervalMean`
  заполнен `Tenure`, чтобы не было NaN);
- `RecencyRatio` = Recency / IntervalMean — «молчит дольше своего ритма?»
  (ожидался как сильнейший сигнал).

**Результат:** качество **не изменилось** ни на одной модели:
- LogReg: ROC-AUC 0.692 → **0.691**;
- CatBoost (early stop): 0.69 → **0.69**.

**Вывод:** все новые признаки выведены из одного источника (даты и суммы
покупок) — несут ту же информацию, что RFM, просто в других формах.
Коррелированные фичи не добавляют сигнала. Задача **data-bound на ~0.69**:
потолок задаёт информационное содержание транзакций одного магазина за год.
Пробить его можно только **внешними данными** (обращения в поддержку,
веб-активность, вовлечённость), которых в датасете нет — не арифметикой над
чеками. Признаки оставлены в пайплайне + задокументирован эксперимент
(демонстрация строгой проверки гипотезы и честного негативного результата).

## Следующий шаг — Этап 7: Интерпретация (SHAP)
- SHAP: какие признаки сильнее всего влияют на прогноз оттока (глобально и
  для конкретного клиента — понадобится в демо на этапе 8)
- Проверить гипотезу из плана: помогает ли признак `Cluster` (метрика с ним
  против без него)
- Анализ ошибок: есть ли сегменты, где модель ошибается чаще
- Потолок ~0.69 уже проверен feature engineering'ом (см. «Эксперимент» выше) —
  не помогло, задача data-bound. Дальнейший рост возможен только с внешними
  данными (поддержка, веб-активность), которых в датасете нет — в бэклог как
  ограничение, а не как задача
